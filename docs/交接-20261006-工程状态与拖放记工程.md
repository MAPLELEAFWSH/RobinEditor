### 3. ⑦ 贴图通道处理：法线那一路（全部落在原有分区里，没加新页）

- **由 R、G 推 Z**：`img.ts` 的 `重写法线` + `ChannelSource.推导 = 'z'`。
  写在 B 那一路上的意思是"R、G、B 三路按法线的写法一起重写"（x/y 取自同一张输出图的 R/G）。
  算式与两个不能省的细节（**每步 32 位浮点**、**写回截断**）在 `docs/产物配对实测.md` §3.5；
  素材里两对真配对**逐像素 100% 相同**（R/G/B/A）。
- 「调换」预设 +3 条、**批量共用同一张表**：`法线·重建 Z` / `法线·翻绿` / `AG 打包 → 标准蓝`。
- **放大核可选**（原来 `pack` 写死 `bilinear`）：双线性 / 最邻近 / 双三次 / Lanczos，默认不变。
  实测一张 4 种材质的 ID 图放大后双线性会数出 **13 种**（插值造的假编号）、最邻近还是 4 种。
  `previewOf` 跟着带核（缓存键含那一档）。
- **认法线**（`texops.ts`）：按四路统计判"标准蓝 / B 不是 z / RG 双通道 / AG 打包"，
  在「通道提取」里显示。判据与门槛是本工程扫 567 张量出来的（见下）。

## 四、这个工程的硬规矩（改之前先看，踩过都在这）

- **改文本文件只用 read / edit / write 工具**，绝不用 PowerShell 的 `Set-Content` / `Out-File`
  （给 `.svelte` 加过 BOM）。
- **别用 PowerShell 匹配/显示中文**：`Get-Content` 显示中文文件会乱码（文件本身没坏），
  `git ls-files | Select-String '开发者指南'` 匹配不上。判断编码要用**字节**量。
- **量之前先证明仪器能复现那个场景**。吃过的亏：`read_rgba` 的桩返回 `{data}` 而不是 `{rgba}`；
  `exe-frontend-check` 的 `hit>0` 结论；`probe-边栏与帧率` 第一版在侧栏已经收起时点"收起"。
- **测过的探针要收拾自己弄脏的状态**：抽屉开合按路由记在 localStorage
  （`robin.wb.side.v3`），探针开着抽屉走 → 下一次 `ui-audit --all` 白报 FAIL。
- `实战测试用例\` 里的原始素材**不许改**，产出写 `测试效果\`；扫语料**排除 `测试效果\`**。
  `D:\MMD模型动作\模型\{…}` 只读。
- **不含、不分发任何第三方渲染包或工具**，别人的**工具名**一个都不许进代码与界面；
  规格来源只有公开文档 + 自己实测（`docs/来源与边界.md`）。
- 开发日志写 `PROGRESS.md`（新一轮加最上面、旧的改"上一轮"），用户提的每条进
  `docs/整改清单.md`，做完标 **已修** 并写清**怎么验的**。
- 界面：侧栏不许出现 ①②③ 序号、错误显示在侧栏、**每页一颗主按钮**、
  动效不许有过冲、模板里不许出现 `**粗体**`（用 `<b>`）。
- **别强行开应用窗口**（用户在跑游戏/全屏时尤其）；能 Node 里验的就别开窗口。
