# ① 日文：还原 + 翻译 —— 作业规格

用户 2026-09-20 的原话：**"可以外接翻译引擎，先修复乱码还原为日文，还可以选择是否翻译为中文；
还有离线翻译修复的另一种后备选择。"** 以及最初的抱怨：**"你的日文翻译根本没有翻译，极其糟糕。"**

## 0. 先认清现状（别再自欺）

`src/lib/modules/glitch/`（① 日文乱码修复）现在干两件事，**没有一件是翻译**：

1. **乱码还原**（`src-tauri/src/textenc.rs`，1165 行 + 22 条 cargo 测试）——
   把"日文按 GBK 读坏"的字节按 GBK 编回去、再按 Shift-JIS 解一次。这一段是**好的**，
   真语料在 `实战测试用例\乱码翻译\`（连文件名都是乱码），别动它的算法。
2. **离线术语表替换**（`glitch/glossary.ts`）—— 把固定说法换成中文。
   它自己的注释里就写着"**它不是机器翻译**，句子的语法结构不管"，界面上也标了"词条覆盖 N%"。

用户在界面上看到"翻译"两个字、用出来却是术语替换，所以觉得"根本没翻译"。**这个错觉是界面造成的**，
本次必须把它删掉。

## 1. 已定口径（用户选的）

| 决定 | 选了 |
|---|---|
| 引擎形态 | **OpenAI 兼容接口**（一个 base URL + 模型名 + Key，同时盖住本机 Ollama / LM Studio / DeepSeek / OpenAI / 各路中转） |
| 翻译范围 | **只翻注释与纯文本，代码一个字符不碰**（`.fx`/`.fxsub` 只动 `//` 与 `/* */`，跟现有还原那条边界一致） |
| 批量翻译 | **这一轮不做**，只做单文件 / 单段。批量那几页照旧只做"还原乱码"（不花钱、不联网） |

## 2. 技术路线（动手前已核实的事实）

- 工程里**没有** http 插件、没有 reqwest；而本工程的既有做法是"文件读写自己写 Rust 命令、
  不用 fs 插件那套权限"（见 `src-tauri/capabilities/default.json` 里的说明）。
  → 翻译请求也**自己写一条 Rust 命令**，不引 `tauri-plugin-http`。
- crates.io **是通的**（`cargo search` 正常；`Invoke-WebRequest` 超时是本工程记过的假阴性）。
- TLS 用 **`native-tls`**（Windows 走 SChannel）：**避开 rustls / aws-lc-rs 在 Windows 上要 NASM**
  那个构建坑，也不给 exe 加一大坨。`CARGO_HOME=D:\Rust`。
- **默认不联网**：引擎配置空着 = 这个功能连一次请求都不发。

## 3. 要做的东西

### 3.1 Rust：`translate_text`

- 入参：`{ baseUrl, model, apiKey, timeoutMs, texts: string[] }`（配置**每次调用传进来**，
  Rust 侧不落盘、不记状态）。
- 出参：`{ ok, translations: string[], error }`。
- 请求：`POST {baseUrl}/chat/completions`，body `{ model, messages: [{role:'system',…},{role:'user',…}], temperature: 0 }`。
- system 提示词：把日文翻成简体中文，只输出译文；保留 `//`、`#define`、`\n` 这类结构；
  不要解释、不要加引号、不要漏行。
- 一次把所有段落拼成带编号的块发过去（省请求数），回来按编号拆开；**编号对不上就整批判失败**，
  宁可报错也不要把译文错位写进文件。
- 错误要**原样透出**（HTTP 状态码 + 响应体前几百字）：`401` 是 Key 不对、`404` 多半是地址末尾少了 `/v1`、
  连接被拒是本机服务没起 —— 界面上要能一眼看出是哪种。

### 3.2 Rust：可翻译段落切分（**复用现有注释扫描，不许写第二份**）

- `textenc.rs` 里已有"只看注释的 .fx 模式"（`fix_fx_comments`）。**把它的注释扫描抽成共用函数**，
  翻译和还原走同一份扫描 —— 两份实现漂开正是这个工程反复吃过亏的地方。
- 纯文本类（`txt`/`md`/`csv`/`log`/`json`/`conf`/`ini`）：整篇算可翻译文本。
- 段落要能**原样写回**（记下每段在原文里的起止），写回时只替换段落内容，
  注释符号、换行、缩进、代码行一律不动。

### 3.3 设置面板：「翻译引擎」一节

- 字段：地址（占位提示 `http://127.0.0.1:11434/v1`）、模型名、Key（密码框）、超时。
- **「试一下」按钮**：发一句固定短句，把返回的译文或**原始错误**显示出来（成功也给看，
  否则用户不知道它到底通没通）。
- 存本机偏好（跟其它 prefs 一起），Key 不上传、只在本机。
- 旁边一句实话：**"只有你填了这里，① 才会发请求；请求只发到你填的这个地址。不填就完全不联网。"**

### 3.4 ① 那一页：两步走，界面不许再含糊

1. **第一步：还原成日文**（沿用现有算法与现有入口，不动）。
2. 结果区里一个开关 **「再翻成中文」**（默认**关**）。打开才发请求；上面写清用的是哪个引擎与模型。
3. **三栏对照**：原文（乱码）/ 日文 / 中文。**中文那栏可编辑** —— 模型翻错的地方人工改回。
4. 落盘：默认**另存**（沿用现有的 `_zh` 一类的后缀模板）；也允许原地写回（留 `.bak`）。
   `.fx` 仍然只动注释、代码一个字符不碰。
5. **离线后备写明白**：没有配引擎时走现有术语表，界面上直接写
   **"离线：术语替换，不是翻译，句子不会翻"**。
   —— 把"看起来像翻译"这件事从界面上彻底删掉，这是用户被误导的根因。

## 4. 验收

1. `pnpm test`（含 `cargo test --lib`）全绿，`svelte-check --threshold warning` 0 错 0 警。
2. **不联网也能跑**：引擎空着时，还原照用、批量照用，且**一次请求都不发**（要有断言钉住）。
3. 请求体的形状有测试钉住（不真发网络请求：测构造出来的 JSON）。
4. 段落切分有测试：`.fx` 里**代码行一个字符都不变**，只有注释内容变；纯文本整篇可翻；
   写回后的文件**除注释内容外与原文逐字节相同**。
5. 拿 `实战测试用例\乱码翻译\` 那批真语料跑一遍还原，把"修完还剩多少没还原干净的"量出来记进 PROGRESS
   （只读素材，产出不许写回素材目录）。
6. 文档同步：`dist\说明.txt` 与 `docs\使用说明-新手向.md` 的 ① 那段要重写；
   **"全程不联网"这个说法必须改准**（改成"默认不联网；只有你自己配了翻译引擎才会发请求"）。

## 6. 追加要求（用户 2026-09-20 原话）

> **"翻译修复模块需要保证乱码可以翻译而不是给我丢回乱码，最起码要修复。"**

也就是说：**不许把乱码原样丢回给用户**。翻译是第二步，第一步的还原**必须真的能修出来**。
按这条，上面 §4.5 量出来的缺口就不是"记录一下"，而是**必须补掉的洞**。

### 6.1 三个缺口（真语料已经证实，不是猜的）

1. **文件名根本没做**：`实战测试用例\乱码翻译\` 里 71 个名字、8 个含非 ASCII，其中 3 个明显乱码
   （`00_僔僃乕僟乕傪嵞攝晍偡傞偲偒偺拄堄揰.txt` 等）。文件正文是好的，**乱的是名字**，
   而现在整个工具对名字一个字符都不动。
2. **短串 / 假名+汉字混排被门槛挡掉**：那 3 个名字修出来是**正确的日文**
   （`シェーダーを再配布するときの注意点` / `追加モーフ` / `アニメ風画面スクリーン`），
   但增益只有 1.44 / 1.55 / 1.75，**差一点没够 1.8**。门槛是按"整段汉字全变假名"（增益 2.4）校准的，
   而这几个修完汉字仍在（每个 +0.6），于是卡在 `部分→魁だ`（增益 1.2）与 2.4 之间那半区。
3. **够不着门槛时界面什么都不给**：只回原文。用户看到的就是"丢回乱码"，连"它其实能修"都看不出来。

### 6.2 怎么做（不许把批量的安全网一起拆掉）

- **a. 单条永远把候选摆出来**（文本页 / 单文件页）：候选、增益、为什么没自动改，逐条列出；
  没自动改就给**「就用这个」**按钮，点了才动手（留 `.bak`）。
  **候选为空才算"真的修不了"** —— 只有这种情况才允许对用户说修不出来。
- **b. 门槛改成按长度/按字符摊**（不是固定 1.8），并补正信号：**假名占比上升**（乱码里几乎没假名，
  这是最硬的信号）；短串（≤4 字）单独一档。**必须一起回归**：
  既有 22 条 cargo 测试全绿，且 `部分→魁だ` 那类假阳性**不许放回来**（那是当初踩过的坑）。
- **c. 新增"名字还原"**：扫文件/目录名里的乱码候选 → 出「原名 → 修后名」表 → 用户勾选后**改名**
  （不覆盖同名、可整体回滚、留一份改名日志）。那 3 个名字就是它的验收靶子。
  ✳ 只读素材不许改：验收在 `实战测试用例\测试效果\` 里造一份副本跑。
- **d. 顺序不变**：先还原成日文，再问要不要翻中文（已有）。名字要不要一起翻成中文**不做**。

## 7. 边界（硬规矩）

1. 语料里那 3 个乱码名字**必须进"可修"表并能真改成正确日文**；
2. 既有 22 条 cargo 测试 + 新增的假阳性用例全绿；
3. 单条输入一段够不着门槛的乱码时，界面**必须给出候选与「就用这个」**，不许只回原文；
4. 批量那条路仍然默认**不自动改不确定的**（安全网不许拆），但要把"看着像乱码但没自动改"的
   单独列出来给用户挑。


- 只读素材不许改，产出写 `实战测试用例\测试效果\`。
- **不许起 GUI 窗口**（用户全屏游戏时被弹窗打断过，已明令禁止）。
- 文本文件只用 read/edit/write 工具改；**绝不用 PowerShell 的 `Set-Content`/`Out-File`**。
- 不搬任何第三方工具的代码、注释、界面文案、操作方式。
- 注释和界面文案按"开发者自己的简短笔记"写，不辩论、不解释设计意图。
