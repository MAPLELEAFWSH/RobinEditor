## 2. B 通道那个"最小最大映射"：形式解出来了

产物 B 不是任何源通道的拷贝，但它是**源 G 的确定点对点函数**：同一输入值在整张图上最多差
**0 级**（0 个冲突值）。所以整张图等价于一张 256 项 LUT，拟合就在 LUT 上做。

抽出来的映射表长这样（星铁 body）：

```
G=  0 → B=255     G= 32 → B=143     G= 64 → B= 31
G= 16 → B=199     G= 48 → B= 87     G≥73 → B=  0
```

斜率恒定 **−3.5**。形如：

```
B = clamp( floor( 255 · (1 − G/hi) ), 0, 255 )        hi 是窗口上端
```

**取整方式是截断（floor），不是四舍五入** —— 这一条是解开的关键。
（拿 `floor(x+0.5)` 或半偶数取整去拟合，最好也只有 81%。）

| 产物 | hi | 取整 | LUT 全等 |
| --- | --- | --- | --- |
| `GI_Converted_Body_Lightmap` | **128** | floor | **100.00%** ✓ |
| `HSR_Converted_Body_Lightmap` | ≈72.86（斜率正好 3.5） | floor | 95.31% |
| `HSR_Converted_Hair_Lightmap` | ≈84（不是 85） | floor | 69.23% → 换 84 更好 |

读出来的三件事：

1. **窗口跟源图自己的 min/max 无关**（星铁 body 源跨满 0~255，窗口只有 0~72.86）。
   所以那不是自动找的范围，是**参数** —— 跟需求里说的"B 通道最小最大映射值的调整"对得上。
2. 原神 body 的 **hi=128 就是 0.5**（归一化后），星铁 hair ≈84 ≈ 0.33，星铁 body ≈72.86 ≈ 0.2857。
   都是**非整数的人填值**，所以后两条永远差最后一两级（残差全是 ±1）。
3. 原神那条**已经完整解决**（LUT 100%）；另两条是端点取整不确定，不是形式不对。

### 怎么落到我们的代码里

`ops.ts` 的 `applyPlan` 是**先 invert 再 stretch**（`extractChannel(…, p.invert)` 然后
`stretchPlane(…, lo, hi)`）。代进去：

```
out = ( (255 − G) − lo ) / (hi' − lo) · 255
```

要它等于 `255·(1 − G/hi)`，取 **`invert: true, stretch: 'manual', lo = 255 − hi, hi' = 255`** 就行
—— 不用改管线，只是 lo/hi 要按这个关系填。原神 body 就是 `lo=127, hi=255`。

**一个要注意的差**：`stretchPlane` 把结果写回 `Uint8ClampedArray`，那是**半偶数取整**，
那份产物用的是**截断**。只在恰好的 .5 上不一样（原神那组 G=64 时正好 127.5：
截断给 127、半偶数给 128）。想逐像素复现就得让这一步能选截断 —— 这是要改的唯一一处。

对不上的 4 个全在星铁，而且全是 B 那个窗口：

- 原神那组的窗口 **128 跨两个角色的 body+hair 都对**，不用一张张调。
- 星铁 **body 是 255/3.5、hair 是 85**（两组样本量下来一致）。
  hair 一开始用了 body 的值，差到 36 级；换成 85 就掉到**恰好 1 级**，跟 body 同一个特征。
- 那 1 级是**浮点**不是语义：`255 − 6×3.5` 在 double 下是 233.999…，floor 得 233
  （实测就是 233）；我们的运算顺序不同，落在 234 那一边。
  要逐像素复现得连它那一步的浮点算式一起复刻 —— 1/255 的差，不值当。
  （原神那组的可行区间是 **[127.5, 128.004)**，用区间求交解出来的，见 `tools/solve-window.py`。）
