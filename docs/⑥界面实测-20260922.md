**怎么做的**：`pnpm tauri dev` 开窗口（给 dev 实例单独指定
`WEBVIEW2_USER_DATA_FOLDER` 和 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`，
**因为用户自己的 `RobinEditor-免安装版` 正在跑、占着同一个数据目录，dev 实例的 webview 起不来**），
再用 CDP（`E:\C test\⑥验收\ui\cdp.mjs`）读 DOM、点按钮、量排版。
**只跑到"试算（不写盘）"，没有写盘** —— 收盘复核：`.emm` 仍是 18:23:51、`.pmm` 仍是 13:33:05、
`E:\C test\达到\盛大的` 里 0 个文件。

输入就是用户自己那套：`…\香港_by_胧月兔_…\UserFile\香港观塘 一键启动 夜间 2.1.pmm`
（导入时同名 `.emm` **自动接上了**，这一条好用）。目标按用户说的选 `E:\C test\达到\盛大的`。

## 0. 先说磁盘现状：这套工程现在是**半改**的

| 文件 | 大小 | 时间 | 里面 172/14 条路径指向 |
| --- | --- | --- | --- |
| `夜间 2.1.emm` | 29200 | **2026-09-22 18:23:51** | 172 条全指向 `E:\C test\达到\…` |
| `夜间 2.1.pmm` | 16840 | 2026-09-22 13:33:05 | 14 条字段仍指向 `E:\deepseek-harness\…` |
| `.emm.bak` / `.pmm.bak` | 17096 / 16840 | 2023-09-24 | 2023 年的原件 |

`E:\C test\达到\` 底下还有 `模型/`、`附件/`、`特效/`、`mmd集成工具/`、`盛大的/` 和另一套 `日间` 的
`.pmm/.emm`（1323 个文件 / 264.6 MB）—— 是用户自己反复试出来的几套落点。

**后果**：`.emm` 和 `.pmm` 对不上，界面报 **「命中率 50%（精确 0 / 结构 7）· 有 7 个对象的路径字段没定位到，写盘会改不全」**。
界面上**没有任何一处**把这件事说成"你的 .pmm 和 .emm 不是一个状态、先把它俩对齐"。

## 1. 真 bug：干跑说"成功"，但它**根本没验路径能不能改**

`干跑 = true` 调 `搬运工程`（映射 `E:\C test → E:\C test\达到\盛大的`）返回：

```json
{ "拷贝文件": 35, "拷贝字节": 17942996, "删除文件": 0,
  "说明": ["干跑：会搬/拷 35 个被引用的文件（约 17.1 MB），并改工程里的路径"],
  "根结果": { "pmm改字段": 0, "emm改行": 0, "旧根残留": [], "新根出现": [], "产物路径": [] } }
```

`根结果` **全是 0** —— 代码里干跑分支直接 `搬根结果::default()` 返回，`if pmm改字段 == 0 && emm改行 == 0 → Err`
那条判据只在真跑分支上。**所以干跑"成功"不代表写盘能成**，界面上那句"并改工程里的路径"是没有依据的。

## 2. 真 bug：`试算失败：undefined` —— 后端报错一个字都没显示出来

界面原文（侧栏提示）：
```
有 7 个对象的路径字段没定位到，写盘会改不全
试算失败：undefined
```

原因：Tauri 的 `Result<T, String>` 拒绝时给 JS 的是**字符串**，而前端写的是 `(e as Error).message`。
实测（`__TAURI_INTERNALS__.invoke` 直接问后端）：

```
typeof e = "string"      ← 不是 Error
string   = "有 179 条换完在盘上找不到 —— 拒绝写盘（没有动任何文件）。前几条：…"
```

`Migrate.svelte` 里 **7 处**都是这个写法（236 / 267 / 306 / 372 / 431 / 470 / 557 行：扫描、打包、保存、换根、搬运、列路径、检索）。
**后果：后端所有拒绝理由用户都看不到**，只看到 `undefined`。这是本轮最伤的一条 —— 工具"宁可不写"的安全设计，
用户完全感知不到，只觉得"点了没反应"。

## 3. 设计问题：搬运卡只给"两段根"，目标又在根里面 → 路径多出一段

搬运卡里给出的根是 **`E:\C test`**（找死根按"两段"分组），而用户要的目标
`E:\C test\达到\盛大的` **就在这个根里面**。同一套映射交给 `搬根` 干跑，它算出来的目标是：

```
E:\C test\达到\…\UserFile\ray-mmd-1.5.2\ray.x
  → E:\C test\达到\盛大的\达到\…\UserFile\ray-mmd-1.5.2\ray.x
                        ^^^^^^ 多出来的这一段
```

也就是说"搬到 盛大的"的**实际结果是 `盛大的\达到\mmd集成工具\…\UserFile\…`**，
不是用户心里那个"UserFile 整个搬到 盛大的"。根太粗 + 目标在根内部 = 多套一层。

同时 `搬根` 在这个映射下**拒绝**（179 条换完找不到）—— 这在"还没拷"的前提下是对的，
但界面只给一句"有 179 条…找不到"，**没有告诉用户"你应该先走 ④ 搬运（它会拷完再改）"**。

## 4. `用这个`按钮：实测确认"点了没反应"是怎么来的

「模型现在在这些目录里」下面 6 行，每行一个「用这个」；而**「新模型目录」已经被预填成第一行**
（`…\UserFile\ray-mmd-1.5.2\Lighting`，11 个模型里只有 5 个在这个目录里）：

```
模型现在在这些目录里
  …\UserFile\ray-mmd-1.5.2\Lighting      5 个（盘上 5）   [用这个]
  …\UserFile\ray-mmd-1.5.2\Fog           2 个（盘上 2）   [用这个]
  …\UserFile\ikBokeh_v019                1 个（盘上 1）   [用这个]
  …
新模型目录  …\UserFile\ray-mmd-1.5.2\Lighting        ← 就是第一行，所以点第一行的「用这个」＝没变化
```

所以"点了没反应"是**必然的**：多数工程这类目录只有一组，而唯一那一行的值早就是框里的值。
另外标签「模型**现在在这些目录里**」和它自己的「盘上 5」是两回事 —— 它是**工程里路径指向哪儿**，
`盘上 N` 才是真有几个。这个块 + 那一对「试算/保存」（按文件名平铺到一个目录）是**老路子**，
跟主路径（根替换 / 搬运 / 检索）并排摆着，容易被当成主路径。

## 5. 文案：面板标题和侧栏 tooltip 还是**旧的三情形**（含已取消的"摘条目"）

面板标题栏与侧栏 `<a title=…>` 现在是：
> 三种情形：文件都在就只把路径指到新位置（不拷贝文件）；**有文件丢了就把丢失的条目从工程里摘掉**、剩下的照常保存（载入不再报缺文件）；也可以把所有文件连同 .pmm、.emm 拷成一个自包含目录。

用户 2026-09-22 明确"**不要做文件丢失的情况了**"，组件里也删干净了 —— 但这层 registry 文案没跟上，
**界面还在承诺一个已经取消的功能**。

## 6. 排版：这一页现在**没有溢出**（① 的全局修在这儿是生效的）

`measure` 结果：`docOver: 0`；320 个候选元素里只有 1 个超出 2px（`.row--stack`，别处的组件）。
长路径那一行（`E:\C test\达到\mmd集成工具\…\UserFile\ray-mmd-1.5.2\Lighting`）**正常断行**，
侧栏提示块也没被撑破。① 的全局断行规则在这一页**实测有效**。

## 7. 其它顺手看到的

- 导入 `.pmm` 后**同名 `.emm` 自动接上**，好用，符合用户"拖入 pmm 就可以了"的口径。
- ② 卡片把"命中率 50%"写在最显眼处，但**没有"下一步该怎么办"** —— 用户看不懂 50% 是什么意思。
- ④ 搬运卡上只有一个组（`E:\C test` 172 条），**看不到"这 172 条到底是什么"**（模型？特效？），
  只能靠猜；③ 卡的目录列表倒是有明细。
- 「每一处路径（逐条）」显示"172 条全部落定"，与 ② 卡的"7 个对象定位不到"看起来矛盾
  （一个说 .emm，一个说 .pmm），界面上没有区分这两层。

## 结论：先修哪几条（建议顺序）

1. **`undefined`**（第 2 条）—— 一行工具函数的事，但它是"用户看不懂工具在说什么"的总根源。
2. **干跑要真验**（第 1 条）—— 干跑也走一遍"换完在不在盘上"的判据，别用 `default()`。
3. **搬运的根粒度 + 目标落在根里面要拦**（第 3 条）—— 现在会多套一层目录。
4. **`.pmm` / `.emm` 对不上要单独说清**（第 0 条）—— 这是用户当前卡住的真正原因。
5. **文案跟上**（第 5 条）、**「用这个」要么删要么改准**（第 4 条）。

**第 1～5 条本轮一条都没改**（用户当时说"先不改这个"）；**第 5 条的 registry 文案已改**（见附）。
