## 1. `.emm`：纯文本 INI，已经量清

不是二进制。CRLF 换行，ANSI（中文系统下 = **GBK**；样本里 `c4 a3 d0 cd b6 af d7 f7` = "模型动作"）
编码，ASCII 键。结构：

```
[Info]
Version = 3

[Object]                      ← 这个工程有哪些对象（模型与附件共用一套序号）
Acs1 = D:\...\ray.x
Pmd2 = D:\...\Skybox\Time of day\Time of day.pmx
Pmd3 = D:\MMD模型动作\...\Flyer\FlyerStage\Flyer.pmx
Pmd4 = D:\...\ray_controller.pmx
Acs5 = D:\...\WorkingFloorAL.x

[Effect]                      ← 每个对象用什么特效
Default = none
Pmd2 = D:\...\Time of day.fx
Pmd2.show = true
Pmd3 = D:\...\Main\main.fx
Pmd3[0] = ...\1.fx            ← **逐材质**：方括号里是材质序号
Pmd3[6] = none
Pmd3[6].show = true
Acs5 = D:\...\WorkingFloorAL.fx

[Effect@EnvLightMap]          ← 还有别的"效果集"分段（EnvLightMap 是其中一个）
Owner = Acs1
Acs1.show = false
Pmd2 = ...\Time of lighting.fx
```

要点（都是量出来的）：

1. **键名 = 对象序号**：`Pmd<N>` 是模型、`Acs<N>` 是附件，**两者共用一套编号**。
   `Flyer1` 那份里实际存在的键是 `Acs1`、`Pmd2`、`Pmd3`、`Pmd4`、`Acs5` —— 中间没有断号，
   说明这个 N 是**对象在 MMD 里的槽位号**，不是"第几个模型"。
2. **`Pmd<N>[m]` 是逐材质特效**：`m` 是材质序号；缺的序号表示那个材质没单独指定。
   `none` 是合法值（= 不指定特效）。
3. **`.show` 是独立的键**（`.show = true/false`），删对象时它也要一起删。
4. **对象顺序**：`.emm` 的编号顺序与 `.pmm` 里模型出现的顺序**不是一回事**
   （`Flyer1.pmm` 里第一个模型是 Flyer，而它在 `.emm` 里是 `Pmd3`）。

⚠ **对"删条目"的影响（这条最要命）**：既然编号是共用槽位号，
**删掉任何一个对象，排在它后面的对象编号都要整体前移**，
`.emm` 里对应的 `Pmd<N>` / `Pmd<N>[m]` / `.show` 键**全部要重写**。
这一步做不对，MMD 打开之后特效就会挂到别的模型上 —— 比不删更糟。

## 2. `.pmm`：二进制，量到了这些

### 2.1 文件头（12 份样本交叉验证，6 KB ~ 89 MB 全部成立）

| 偏移 | 类型 | 实测到的值 | 判据 |
|---|---|---|---|
| 0x00 | char[24] | `Polygon Movie maker 0002` | 全部样本一致（写 `0001` 的是 PMM 1.0，见下） |
| 0x18 | ? | 全 0 | 12/12 为 0，**含义未定** |
| 0x1E | uint32 | 1920 / 3840 / 4096 | 12/12 落在合理屏幕宽 |
| 0x22 | uint32 | 1080 / 900 / 1842 / 2160 | 12/12 落在合理屏幕高 |
| 0x26 | uint32 | 279 ~ 405 | 全部是小整数，**像帧数**（未证） |
| 0x2A | float32 | 24.0 / 28.0 / 30.0 / 31.0 | 是帧率（有两份是 2.0，待查） |
| 0x2E | uint8 × 7 | 多为 1（个别第一字节为 0） | 像"有哪些东西"的开关，**含义未定** |
| 0x35 | uint8 | 0 ~ 19 | **计数之一**（`ANTU` = 17） |
| 0x36 | uint8 | 3 ~ 43 | **计数之一**（`ANTU` = 26） |
| 0x37 | uint8 | 全 0 | 含义未定 |
| 0x38 | — | 第一个模型条目的名字长度 | 见 §2.2 |

> 说明：0x35/0x36 到底是什么计数（模型数？对象数？）**还没定死**。
> `ANTU.pmm`（17 / 26）与 `ANTU1.pmm`（+62 字节）差分时，**第一个分歧字节正好在 0x35**，
> 说明它确实是"跟着对象增减变"的计数字节之一，但哪一个对应什么还没验出来。

### 2.2 模型条目（`Flyer1.pmm` 实测）

```
0x38  uint8  名字长度（字节数）
0x39  char[] 模型名（Shift-JIS；这里是 "Flyer"）
      uint8  英文名长度
      char[] 英文名（"Flyer"）
      char[256] 路径（**定长 256，0x00 补齐**）
```

- **路径是定长 256 字节、没有长度前缀**。判据：路径起点 + 256 正好落在路径之后第一个非零字节上，
  三份样本都成立（`Flyer1`：0x44 + 256 = 0x144 ✓）。
- **路径编码是 ANSI（中文系统 = GBK），不是 Shift-JIS**。实测
  `44 3A 5C 4D 4D 44 C4 A3 D0 CD B6 AF D7 F7` = `D:\MMD模型动作`。
  → 迁移时写回也要按同一套编码，否则 MMD 读不出来。
- 名字的长度是**字节数**（`08` + `83 5A 83 93 83 5E 81 5B` = "モデル"，4 个日文字 = 8 字节）。
- 名字/英文名之间没有别的字段，紧挨着。

### 2.3 模型条目之后要解的那一段（**还没解完**）

`path[256]` 之后到"下一个模型的名字"之间，是那个模型自己的数据（实测 644 字节的一例），
里面能看到两种名字：**骨头名**（`モデル`、`SunRadius+`、`SunPhase-`…）和另外几个
（`Off Screen 1` / `Off Screen 2`）。**这一段的记录边界与计数还没定死**，见 §4。

### 2.4 附件条目

附件同样有名字、英文名、路径（`ray.x`、`WorkingFloorAL.x` 都在文件后半段），
**位置在模型区之后**。它的变换字段、关键帧、以及它自己的计数**还没解**。

### 2.5 一个必须记住的坑：文件里可能有"未初始化内存"

`ANTU.pmm` 里能看到成串的 `… F9 7F 00 00`（Windows 堆指针形状）和类似地址的值。
**这些字节不是格式的一部分**，是 MMD 写文件时留下的垃圾。
→ 我们的工具**绝不能去解释或重算这些字节**，只能原样搬运；
凡是"重排/重建结构"的想法都必须放弃，一律按"就地剪切 + 改计数"来做。

## 3. 迁移功能的落点（由以上量测直接推出）

工程需要用到的文件分两处登记，**两边都要改**，缺一边 MMD 都不会好：

1. **`.pmm` 里**：每个模型/附件的路径（定长 256 字节，ANSI 编码）—— 改路径就改这里。
2. **`.emm` 里**：`[Object]` 的 `Pmd<N>` / `Acs<N>` 路径、`[Effect]` 的 `Pmd<N>` /
   `Pmd<N>[m]` / `.show` 键、以及 `[Effect@…]` 那些附加段 —— 逐材质特效也在这里。

而**贴图路径不在这两个里**：`.pmm` 只有模型/附件路径，贴图是模型 `.pmx` 自己带的信息。
→ "全都要拷进输出目录" 这件事，需要**再解析 .pmx / .x 找它们引用的贴图**，那是另一块活。

## 4. 还没量清的（**不确定，明说，不猜**）

1. `path[256]` 之后那段（骨头/形态关键帧）的**记录边界**：一个模型的这段有多长、
   里面有几个计数要改 —— **这是"删条目"能不能做对的关键，还没定死**。
2. 附件条目的完整布局（名字之后有哪些字段、附件关键帧怎么存）。
3. 0x35 / 0x36 两个计数各自的含义（哪个是模型数、哪个是对象数）。
4. 0x2E 那 7 个开关字节、0x26 是不是帧数、`0x18` 那 4 个字节是什么。
5. 文件里有没有**绝对偏移/指针**（若有，剪切之后必须重算；目前没发现指向文件内部的偏移）。
6. 两份样本里 0x2A 的帧率是 2.0（不是常见的 24~31），原因未查。

## 5. 下一步怎么量（工具都在了，照这个顺序）

1. **用 `pmm-diff.py` 找记录边界**：继续拿"几乎相同、长度不同"的成对样本
   （`ANTHU`/`ANTHU1`、`ANTHU1`/`ANTHU2`、`千盏`/`千盏1`、`璃`/`璃2`、`Nadir`/`Nadir(1)`）
   做差分，分歧处的偏移就落在记录边界上；配合长度差反推被增删的那一段多长。
2. **写一个"必须恰好读到文件尾"的走读器**：把猜的结构写成解析器，喂多份大小不同的样本，
   **只有能一丝不差走到 EOF 的假设才算对**（这是判格式假设最硬的判据）。
3. **用 `.emm` 反证**：`.emm` 的 `Acs<N>`/`Pmd<N>` 编号顺序必须能从 `.pmm` 里推出来；
   推不出来就说明模型区里还有一个"槽位号"字段没找到。
4. 附件区单独解：从 `ray.x` / `WorkingFloorAL.x` 这类**只出现一次**的短路径附近下手，
   比在模型区里混着猜容易。
5. 全部解完再动功能代码。**这一轮一个功能字节都没写。**

## 6. `.pmx` 贴图引用：量清了

**结构**（公开结构 + 本工程实测一致，`ray_controller.pmx` 等）：

```
"PMX " + float 版本(2.0/2.1) + uint8 全局数(8) + 全局[8]:
    [0] 编码 0=UTF-16LE / 1=UTF-8      ← **贴图路径按这个编码存**
    [1] 追加 UV 数   [2] 顶点索引宽度  [3] 贴图索引宽度  [4] 材质索引宽度
    [5] 骨骼索引宽度 [6] morph 索引宽度 [7] 刚体索引宽度
四个字符串（本名/通名/注释/注释英）：**int32 字节长度 + 内容**
int32 顶点数 + 顶点区 + int32 面索引数 + 面区
int32 贴图数 + 贴图路径 × N              ← **贴图引用在这里**
材质区：每材质含 贴图索引 / 球面贴图索引 / toon（索引或共用序号）+ memo + 面数
```

1. **贴图路径 = "int32 长度 + 字节"的可变长字符串**，编码看头部全局[0]。
2. **材质按索引引用贴图，不是按偏移**（实测 `贴图#0`、`球面#-1`、`toon#-1`；`-1` = 无）
   → **改一条路径的长度不需要修任何偏移**。
3. **往返验证**：真模型造副本，`main1.png`（18B）→ `素材\main1_texture_v2.png`（46B）：
   文件 2,425,285 → 2,425,313（**正好 +28**）、布局不变、贴图 2 条不变、其余贴图逐条一致、
   **80 个材质的引用一条没变**。
4. **删一条贴图就不一样**：贴图数是显式 int32，删一项后面序号全前移，而材质里有
   **三种引用**（贴图/球面/toon）都要改 → "删表项"代价明显高于"放占位图"（见 §6.5 第 4 条）。
5. **野生 `.pmx` 有布局变体**：抽查 180 份，**SDEF 段 36B 的 178 份、40B 的 2 份**。
   只按 36B 写解析器会在这 2 份上**读错贴图表**（路径变垃圾 → 打包时以为它没贴图）。
   → 解析器必须**自带布局拟合 + 语义校验**（校验：贴图路径能不能在盘上找到）。
   加上变体回退后 **180/180 全部解析成功**。
6. **缺贴图是常态**：180 份 × 171 条引用，**20 条（11.7%）在盘上找不到**。

## 7. `.pmm` 路径字段：改写**可以原地做**

- 条目形状（实测）：`uint8 名字长 + 名字(SJIS)` + `uint8 英文名长 + 英文名` + **`char[256] 路径(GBK)`**。
- **推翻我之前那条判据**："字段尾部补零 ⇒ 能当识别判据"。实测 ray_controller 的字段尾部是
  `…ray_controller.pmx\0Time of day.pmx\0` —— **残留着上一次写入的更长的路径**。
  字段是定长 256，但**内容不清零**。（我第一版用"尾部补零"识别，只认出 2/5 条。）
- **用 `.emm` 当锚定位字段**：`.emm` 的 `[Object]` 段带同一批路径文本，拿它在 `.pmm` 里搜：
  30 个真工程、**966 条路径 100% 各命中唯一一处** —— 不需要先解关键帧区。
（**这句的样本太小，已在 §第七轮 更正**：实现方在 133 工程 / 4501 条上量到唯一命中 **69%**，
以实现方数字为准。）

## 10. 头部计数反证：**0x36 = 模型数**（量实）

拿 `.emm` 的 `[Object]` 数当参照，40 个真工程：

| 假设 | 命中 |
|---|---|
| **0x36 = 模型数（#Pmd）** | **37 / 40（92%）** |
| 0x35 = 附件数（#Acs） | 2 / 40 |
| 0x36 = 附件数 | 2 / 40 |
| 0x36 = 模型数+附件数 | 1 / 40 |
| 0x35 = 模型数 | 1 / 40 |
| 0x35 = 模型数+附件数 | 0 / 40 |

→ **`0x36` 就是模型数**（删模型要减它）。**`0x35` 既不是模型数也不是附件数**，含义仍未知
（不是"没量"，是"量了，跟对象数对不上"）。附件数**没在头部找到**（`0x35/0x36` 都对不上），
附件区之前也看不到明显的计数字段 —— 附件数从哪来**仍然没解**。

## 11. 附件条目：**名字[100] + 路径[256]**（量实）

同一份 `Flyer1.pmm` 里两个附件各自对上（差值正好 100）：

| 附件 | 名字在 | 路径在 | 差 |
|---|---|---|---|
| `Acs1` = `ray.x` | 5,460 | 5,560 | **+100** |
| `Acs5` = `WorkingFloorAL.x` | 5,912 | 6,012 | **+100** |

→ **附件的名字是定长 100 字节字段（0 补齐），没有长度前缀**；模型则是两个长度前缀名字。
路径仍是 `[256]`，与模型一致。路径之后有一段附件数据（本样本 96 字节，里面有
`01 FF FF FF FF` 与 `1.0` 浮点，像变换/可见性）。

**这条修正了一个我自己的错**：第一版把附件按"长度前缀名字"往回找起点，
于是算出的帧区长度出现负数（-356 = 100 + 256），批量切只有 1/40 干净。

## 12. 帧区边界：用 `.emm` 锚能切，但**记录内部还没解**

按条目形状（模型/附件各一套）算出条目起点 → 相邻两条目之间就是"中间那个对象的帧区"。

**结果（30 个真工程）**：**20 个能把整份文件切干净、首尾相接不留缝**（修附件布局前是 1/40）。

# 第十轮：**附件数定论 —— 没有计数字段，它由附件块里的序号推出来**

量具 `tools/pmm-acs-count.py`，36 个"能对账"的工程（`0x36` == 模型数）：

| 假设 | 命中 |
|---|---|
| ① 头部 `0x2E..0x3F` 里有 #Acs | 7/36（都是**巧合**：同一位置在不同工程上对不上） |
| ① 头部里有"模型数+附件数" | **1/36** ✗ |
| ③ 附件区之后 64 字节里有 #Acs | 2/36 ✗ |
| ③ 附件区之后有"总数" | 1/36 ✗ |

三条假设**全部否掉**。但同一批输出的**块首 u32** 给出了真正的答案：

| 工程 | #Acs（`.emm`） | 最后一个附件块的首 u32 |
|---|---|---|
| `Main ( LeoNeed Team )` | 1 | **0** |
| `Addiction` | 18 | **17** |
| `Cat Loving` | 15 | **14** |
| `DAYBREAK FRONTLINE` | 20 | **19** |

→ **附件块首 u32 是 0 起的附件序号，且序号稠密 0..n−1**（与 §17 的 `ANTU` 六个附件 0..5 一致）。
**附件数 = 所有附件块首 u32 的最大值 + 1** —— 它不是"存着的"，是**推出来的**。

## 41. 可执行结论（一句）

> **删附件没有"计数"字节要改**。`⑥` 只需：① 按 §32 的链把那个附件条目**整段摘除**
> （起点 = `名字[100]` 字段起点，止点 = 下一个条目起点）；② 把**其余附件块首 u32 里 > 被删序号的各减 1**
> （保持 0..n−2 稠密）；③ `.emm` 按 §18 重写键（`Acs<N>` 及其 `.show`、`Pmd<N>[m]`）。
> **不需要找任何计数字段**；**模型侧**要改的仍是 `0x36..0x37`（uint16 模型数）。

→ **B 现在可以支持删附件**（对用户那条 `Acs7` 直接有用）。
遗留一条（不必先解决，但要知道）：序号是稠密的，"删一个却不改其余序号"MMD 那边会不会接受**未验**；
本工程按"保持稠密"（与 §18 的 `.emm` 规则一致）处理，不赌。

> 【补回 §12 被误删的一段】**帧记录布局仍未定死**：帧区开头的几个字节是什么意思还没解
> （`Pmd3` 是 `04 01 00 00 00 …`、`Pmd2` 是 `03 01 00 00 00 …`；**不当槽位号**，
> 因为 §38 已用 479 个样本定论"模型帧区里没有稳定的槽位号"）。这一条只影响"改关键帧"，
> **不影响删条目**（删条目靠边界整段摘除）。


**剩下的 10/30 为什么切不干净**：负长度恒为 **-356 = 100 + 256**，指向两类原因：
① 同一路径文本在文件里出现多次（我取的是**第一处**，可能取到另一条对象里的同一路径）；
② 有些工程里对象在文件中的先后顺序与 `.emm` 的编号顺序不成单调关系。

## 16. 帧区边界：锚点法可用，但被**重复路径文本**污染（本轮定位到根因）

上一轮"30 个工程 20 个切干净、10 个切不干净"，本轮把根因量出来了：

- `.pmm` 里**同一段路径文本会出现多次**（路径字段是定长 256、**写入时不清零**，
  旧的长路径片段会残留在其它字段里，见 §7）。
- 我按"全局搜第一处"定位路径字段，于是**可能定到残留里那一处**，
  算出来的帧区长度为负（恒为 **-356 = 100 + 256**，正是"附件名 100 + 路径 256"）。
- 例子：`Flyer1` 里 `ray_controller.pmx` 的路径文本至少出现在 2 处，

→ **结论**：要可靠定位，必须"按结构逐条目推进"，而推进需要帧区长度 —— **又回到帧记录布局**。
所以**纯 `.pmm` 走读器仍然做不出来**（这一轮的硬结论）。但注意：⑥ 的流程本来就要求
用户**同时导入 `.pmm` 和 `.emm`**，用 `.emm` 当锚 + 结构校验（附件块以 `名字[100]` 开头、

# 第五轮：把"删条目"的四件往前推（结构扫描）

## 23. 附件数：**头部里没有**

② MMD 靠"读到文件末尾/遇到下一段标志"来界定附件区（**没有计数字段**）；
③ 计数在**附件区之后**（摄像机/灯光段附近）。

**不足以当结论**。要证有/没有，下一步应当：
① 用本轮的**结构扫描器**（不再靠路径定位）取出所有模型帧区的首字节，
与 `.emm` 槽位逐个对齐，看是否稳定等于"槽位 + 1"或"槽位"；
② 若稳定成立 → **删模型后必须改其余模型帧区里的这个值**，这是"删条目"最容易漏的一步。

# 第七轮：给实现方的**定位判据**（可直接照做）

**先更正一句话**：我前面写的"966 条路径 100% 唯一命中"只覆盖 **30 个工程**；
实现方在 **133 个工程 / 4501 条对象**上量到 **唯一命中 69%**。**以实现的数字为准**，
那句 100% 是样本偏小造成的（小工程多、路径重复少；大工程里同一路径文本重复出现更频繁）。
下面这套判据就是为了把这个比例压上去、并把"不确定"的情形**挡在门外**。

## 30. 候选形状（必要条件，两条都不满足就不是条目）

```
模型块： u8 名字长(1..60) + 名字 + u8 英文名长(0..60) + 英文名 + 路径[256]
附件块： 名字[100]（NUL 结尾，且其后到第 100 字节必须全 0） + 路径[256]
```

- 名字/英文名：逐字必须是合法 Shift-JIS 单/双字节或可打印 ASCII，**不许出现 < 0x20 的控制字节**。
- 路径字段：取第一个 `\0` 之前的内容（**没有 `\0` 就整段 256 字节都算**，见 §33 截断）；
  内容里不许有 `\0` 之外的 < 0x20 字节；**必须含 `:` 或 `\`**。
  ⚠ **不要把判据放宽到"相对路径也算"**：实测把 `X.pmx` 这种也收进来之后，
  批量判据从 **16/30 掉到 4/30** —— 残留片段本身就是"像相对路径的短串"。

## 31. 排除"残留"（定长字段写入不清零造成的假候选）

路径字段**写入时不清零**，旧的长路径会残留在别的字段里（实测 `Flyer1`：
`…ray_controller.pmx\0Time of day.pmx\0`）。这些残留也能凑出"像条目的形状"，所以：

1. **附件**：`名字 == 路径的文件名`（basename，忽略大小写）。**不满足就拒绝**。
   —— 这条是附件侧唯一需要的排他判据，实测加上之后附件数在抽查工程上与 `.emm` 的 `#Acs` **逐一相等**。
2. **模型**：名字**不要求**等于文件名（用户会改模型名），改用这四条：
   a. 路径必须以 `.pmx` 或 `.pmd` 结尾（忽略大小写）；
   b. 名字长度 ≥ 1 且英文名长度可为 0；
   c. **名字里不许含 `\` `/` `:`**（残留片段常整段就是路径，实测抓到过
      "名字" = `ay-mmd-1.5.2\ray_controller.pmx` 这种假条目）；
   d. 英文名同样不许含路径分隔符。
3. **顺序约束**：**模型条目必须全部排在附件条目之前**（所有干净样本都是"模型区在前、附件区在后"）。
   夹在模型之间的附件候选、或夹在附件之间的模型候选 → 当残留丢弃。
4. **不重叠**：`下一条目起 ≥ 上一条目起 + 该条目的头长度 + 256`（路径字段不许压进下一条目）。

## 32. 多条候选怎么筛 / 什么时候必须拒绝

把通过 §30+§31 的候选按偏移排序，求一条**满足下列全部条件**的链（取总分最高的链）：

1. **帧区长度 ≥ 0**：`条目[i+1].起 − (条目[i].路径起 + 256) ≥ 0`；
2. **模型在前、附件在后**（§31.3）；
3. **模型数 == `0x36`** —— 这是最强的一条（实测 40 个工程里 37 个与 `.emm` 的 `#Pmd` 严丝合缝）；
4. 有 `.emm` 时：**附件数 == `.emm` 的 `#Acs`**，且每个条目的路径能对上 `.emm` 里的一条（一一对应，不重复用同一个键）。

**打分建议**（用于在多个可行链里挑，以及在超过数量上限时裁剪）：
`名字 == basename(路径)` **+3**；名字里无分隔符 **+2**；路径以 `.pmx/.pmd/.x/.fx` 结尾 **+2**；
英文名非空 **+1**；**路径字段 256 全满且无 `\0` −3**（截断特征，见 §33）。

**必须拒绝（不许猜）的情形** —— 任何一种出现就整份文件停下、报"结构校验未通过"，**不要尝试修补**：

| # | 情形 | 为什么拒绝 |
|---|---|---|
| 1 | 说得通的模型候选数 **≠ `0x36`**（多或少） | 多往往是残留、少是漏检，两种都会让"删哪个"变错 |
| 2 | 找不到满足 §32.1 的链（出现负帧区） | 说明有条目没被扫出来 |
| 3 | 同一对象有**多条说得通的候选**，且无法用模型数/附件数/顺序区分 | 猜错就等于改坏工程 |
| 4 | 有 `.emm` 而两边对象数不一致 / 有 `Acs*` 键找不到对应条目 | 两边必须一一对应才敢动 |
| 5 | 路径字段是**截断**状态（§33） | 尾巴不在文件里，补不出来 |

## 33. "被 256 截断的路径"怎么认（可判据特征）

路径字段是**定长 256、不存长度**，所以超长路径会被截断，**尾巴本来就不在文件里**。判据：

- **截断**：`字段 256 字节全满` 且 `找不到 \0` 且 `结尾不是可识别扩展名（.pmx/.pmd/.x/.fx/.fxsub/.accessory）`
  —— 例：`D:\很长\很长\FlyerSta` 这种半截路径。
- **正常但用满**：256 字节全满、无 `\0`，但**以扩展名结尾** → 合法（路径正好占满）。
- **残留**：`第一个 \0 之后仍有非零字节`（例如 `…\Flyer.pmx\0Time of day.pmx\0`）
  → **解析只看第一个 `\0` 之前**；**写回时把整段 256 先清零再写**（安全，实测原地覆写已验证）。

**截断路径的行为**：① **不要**去同目录"按前缀猜是哪个文件"——猜错就是改坏工程；
② 标成"路径不完整"，交给用户指定对应文件；③ 写回时**必须 ≤ 255 字节**（否则又把字段写满）。

## 34. 三件老问题的本轮状态

1. **路径定位改成结构校验**：本地量具做到 **16/30**（判据见 §30–§33；30/30 未达到）。
   失败样本逐条：`Cat Loving` 9/12、`DAYBREAK FRONTLINE` 9/15、`Infinitely Gray` 9/13、
   `NEON BLADE` 15/19、`Supernova` 11/15；也有多扫的（`ANTU` 26/25）。
   两次放宽（解码放宽到 SJIS、判据放宽到相对路径）都被实测否掉，**别再放宽，改成照 §32 拒绝**。
2. **附件数**：**没找到**（`0x35`/`0x36` 都不等于 `#Acs`；附件区前是成片 0）→ **不做删附件**。
3. **帧区里的模型序号字段**：附件侧**有**（块首 u32 = 0 起序号）；模型侧**未定**。
   定它的办法：拿 §32 通过的链，取每个模型帧区首字节与 `.emm` 槽位相减，看差值是否恒为 1/0；
   **恒为定值才叫"有"**，否则按"没有"处理。

# 第八轮：两件事的实测结果（一正一反）

## 35. `0x35`：**"合成 16 位"这个方向被否掉；顺带定死 `0x36..0x37` 是 uint16 模型数**

量具 `tools/pmm-slot-field.py`，25 个"能对齐模型数"的工程：

| 假设 | 与模型数吻合 |
|---|---|
| `u16 @ 0x34` | **0 / 25** ✗ |
| `u16 @ 0x35` | **0 / 25** ✗ |
| `u16 @ 0x36` | **25 / 25** ✓ |

→ ① `0x34..0x35`、`0x35..0x36` 合成 16 位**都不成立**（这就是你要试掉的那个方向，**否掉了**）。
② **`0x36` 与 `0x37` 合成一个 uint16，值 = 模型数**（25/25 严丝合缝；`0x37` 恒为 0 是因为模型数 < 256）。
→ 删模型时按 **uint16 写回 0x36..0x37**，不要只动一个字节。
③ `0x35` 仍然未知，但它**已经排除**：模型数、附件数、总数、以及各种 16 位合成。

## 36. 帧区模型序号字段：**本轮没得出定论（我的配对逻辑写错了，如实报）**

量具里"按名字/路径把条目对到 `.emm` 键"那一步我写错了（拿 basename 去比整条路径），
于是**配上的对子是 0 个**，差值分布是空的 —— **这一条本轮没有结论**，不能说"有"也不能说"没有"。

**下一步（已经很明确，照做即可）**：用 §32 的链 + `.emm` 的 `[Object]` 路径**逐条精确匹配
（整条路径字符串相等，不是 basename）**，取每个模型帧区首字节减槽位，统计差值：
**差值恒为同一个常数（如 1 或 0）才算"有"**；分布散乱则算"没有"。
`Flyer1` 那两个样本给出的 4 与 3（槽位 3 与 2）**只能当线索**，不能当结论。

## 37. 附件数：**仍然没找到 → 删附件当前不可做**

已排除：`0x35`、`0x36`、`0x36..0x37`（= 模型数）、"附件区之前的字节"（成片 0）。
剩余可能：① 与模型数共用一个"总对象数"（但头部没有对齐的字节）；② MMD 靠"下一段标志/文件尾"界定附件区（**根本没有计数字段**）；③ 计数在附件区**之后**（摄像机/灯光段附近）。
**结论：在找到之前，⑥ 不做删附件**（删模型不受影响，`0x36..0x37` 已定）。

# 第九轮：槽位号定论 + 删除步骤（写进规格，不再只躺在量测笔记里）

## 38. 模型帧区里**没有**槽位号（定论）

修正了配对 bug（上一版拿 basename 比整条路径 → 配上是 0 个）之后，改成**整条路径字符串精确匹配**，
在 25 个"能对齐模型数"的工程上配到 **479 个模型帧区**，取"帧区首字节 − `.emm` 槽位"：

**差值散成一大片**（实测出现 −39、−38、−37 … −25、−24、−23 等许多互不相同的值，每种只出现 1~3 次），
**不存在任何一个恒定常数**（`Flyer1` 那两个样本给出的"槽位+1"是巧合）。

→ **定论：模型帧区里没有"这是第几个模型"的槽位号字段** → **删模型时不需要去改其余模型帧区里的字节**。
（保留一句留白：差值散乱也可能因为少数条目的帧区起点被残留污染；但即使如此，
"存在一个恒定常数"这个假设**没有任何样本支持**，按"没有"处理是对的。）
✳ 附件侧相反——**附件块首 u32 是 0 起序号，那条是量实的**（§17）。

## 39. 删模型的步骤（把 `0x36..0x37` 这条写进流程，别只留在量测笔记里）

1. 用 §32 的链确定要删的条目的**起止**：起 = 条目起点（名字长度字节），止 = 下一个条目起点；整段摘除。
2. **计数按 uint16 写回**：`0x36..0x37` 是一个 **uint16 模型数**（实测 25/25 工程严丝合缝），
   **减 1 后按 2 字节写回**（只动 `0x36` 一个字节在模型数 > 255 时会写错，本工程样本里没到 255，
   但按 uint16 处理才是对的）。
3. `.emm` 按 §18 规则重写（删编号 N、其后整体减 1、`.show` 与 `Pmd<N>[m]` 跟着减、`[m]` 不变）——
   已验证。
4. **不需要**改其它模型帧区里的字节（§38 定论）。
5. **不许动** `0x35`（含义未知，没有任何证据说它跟对象数有关）。

## 40. 模型条目识别的剩余不确定性（**定稿，给实现方按"拒绝 + 报告"跑**）

- **可靠**：附件条目（形状 + `名字 == 路径文件名` + `.emm` 的 `#Acs` 与路径一一对应）。
- **不可靠**：**模型条目**。本地量具最好只到 **16/30**；四个方向试过——
  解码放宽（无变化）、相对路径放宽（更差）、顺序约束（无变化）、数量约束（已在用）——**全部回退**。
- **所以实现方按这条跑**：用 `0x36` 当**主约束**、形状判据当**校验**；
  **模型候选数 ≠ `0x36` 就整体拒绝**（§32），**报告"结构校验未通过"并列出歧义候选**，
  **绝不尝试挑选或修补**（挑错等于把路径写到错误位置，比拒绝危险得多）。
- **删模型因此在实现里应当是"能算则算、算不准就拒绝"**，不允许"尽力而为"。
- **解除条件**：拿到"同一工程删掉中间一个模型前后两份 `.pmm`"的配对样本（受控实验），
  用差分一次定死帧区长度与条目边界；在那之前**不要**再试字节特征。

## 41. 模型**名字**：能读、能**等长**改；改长度**不做**（实测）

参考工具那页是「名称 + 路径」两个字段（`l10n\zh-hans.xml` 的 `labelModelName` / `labelModelPath`），
所以名字这一项我们也要能看能改。格式与实测如下。

### 41.1 名字怎么写（复述 §2，便于一处查）

- 模型条目 = `[u8 名字长][名字 n1][u8 英文名长][英文名 n2][char[256] 路径]`（名字是**字节数**长度前缀）。
- 附件条目 = `[名字 100 字节区][char[256] 路径]`（NUL 结尾、其余补零，**没有长度前缀**）。
- 编码**没有标记**：按原文回推 —— 先用 Shift-JIS 解、能原样编回去就是它，否则按 GBK
  （MMD 中文版会把中文名按 GBK 写进名字段，实测）。

### 41.2 改长度会怎样：**实测 8/8 工程上我们自己的结构自检失效**

量具：`cargo test --lib -- --ignored --nocapture 真工程改名实测`（8 个真工程，两种改法各跑一遍）：

| 改法 | 结构条目数 | 本条目还认得出 | 路径命中 | 长度差 |
|---|---|---|---|---|
| **等长**（字节数一样） | 不变 | **是** | 不变 | **0** |
| **变长**（+9 字节） | 不变 | **否** | **-1** | +9 |

丢的永远是**被改名的那一条**（`Pmd2`，名字里含日文，SJIS 编码的**尾字节出现 `0x5C`**）——
`名字像路径` 这个假阳性过滤器把 `0x5C` 当成路径分隔符，于是整条被拒。

**所以结论有两条，必须分开说**：
1. **文件本身可能没坏**（条目数、模型数都没变），**但我们无法再证明它没坏** ——
   工具的自检在改长度之后失效，等于盲写。
2. 于是**只放行等长改名**（`搬家` 里 `新字节.len() != 原名.len()` 直接 `Err`，
   并且把"原名多少字节、新名多少字节"写给用户看）。**改长度不做**，不是没时间，
   是"量不清就不做"。

**要解锁"改长度"**，得先修 `名字像路径` 那条判据（把 SJIS/GBK 的尾字节 `0x5C` 与真分隔符区分开），
再重跑这个量具、确认 8/8 都不掉定位；在那之前不许放。另：**MMD 能不能接受长度变化后的工程，
本工具验不了**（要用户开一次 MMD）。
